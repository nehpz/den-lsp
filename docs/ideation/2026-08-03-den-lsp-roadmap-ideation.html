den-lsp Roadmap — Focus Areas and the Operating Loop

Date 2026-08-03 Topic den-lsp-roadmap Focus roadmap derived from STRATEGY.md Mode repo-grounded

Four focus areas and an explicit operating loop, distilled from 42 raw candidates across five ideation frames, verified against the codebase, cut by adversarial review, and restructured after refinement. The governing principle: this is not a waterfall that perfects the tool in the lab and then meets reality — the lab exists only to prove one claim (existing fixtures produce findings agents actually resolve), after which the field becomes the primary evidence source. Sequencing is a bootstrap, not a lifecycle: CI gate → minimal evidence kernel → field readiness, then the loop runs.

Grounding Context

Codebase context. The pipeline is a vendored capture layer (nix/den-analysis.nix, Analysis IR v1) feeding a pure Nix rule engine (nix/engine/, 6 rules: 4 gating, 2 advisory) that emits a versioned findings document with prose-only message/fix/docRef fields. Two consumers: the flake check gate + den-lsp-check CLI, and a Rust tower-lsp server that spawns nix eval --json on save (300 ms debounce, no subprocess timeout, no CodeAction support, location fallback to flake.nix:0,0). Track maturity: semantic quality medium, agent feedback loop medium, evaluation & evidence low (no harness exists despite all four strategy metrics being harness-defined; CI publishes to FlakeHub without running tests), analysis contract high/stable.

Institutional memory. Deep serialization of emitted class modules is unsafe in pure Nix (missing-attribute errors are uncatchable by tryEval); emission stays lazy behind a declared flag; walking emit-class parameter context can explode on absent flake inputs; the analysis layer is vendored deliberately to work against stock den ≥ 0.18.0.

Field evidence. A sniff-test run against a real, agent-touched den repo surfaced multiple den-lsp bugs that clean lab fixtures never triggered — direct evidence that real-world configurations are the defect distribution that matters, and that field exposure cannot wait for lab polish.

External context. Nix-ecosystem linters (statix, nil, nixd, deadnix) are syntactic — the evaluated-graph position is uncontested. Adjacent prior art: policy-over-evaluated-config (OPA/conftest on Terraform plans, Kyverno, CUE). 2026 agent-tooling signal: "Actionable CI" pairs analysis with LLM-readable explanation and autofix; seeded-defect evaluation maps to mutation-testing prior art. For agent delivery, a JSON-emitting CLI beats a resident protocol server here: den-lsp's latency is dominated by nix eval (amortized by the eval cache across invocations, not by a daemon), and MCP's strengths — auth boundaries, stateful sessions — have no counterpart in this tool. No docs/solutions/ learnings store exists yet.

Topic Axes

  • rule-coverage — what the engine can detect in the evaluated graph
  • repair-guidance — fix-shaped findings, machine-actionable fixes, explanation quality
  • feedback-delivery — LSP/CLI/check channels, eval speed, reliability

Ranked Ideas

Focus areas (order = bootstrap sequence; steady state is the loop)
  1. Evidence kernel — prove the fixtures, no more
  2. Field readiness — usable in the wild, early
  3. Machine-actionable repairs
  4. Coverage expansion

1. Evidence kernel — prove the fixtures, no more

Bootstrap 1 measurement-harness Confidence 90% Complexity Medium

Description: The minimum evaluation capability that proves one claim: the existing clear-cut fixtures produce findings a coding agent can actually resolve. Deliberately scoped to what already exists — hand-seeded fixtures, no mutation engine, no fixture factory. What the kernel teaches feeds Focus 4's rule design and is reinforced (or corrected) by field results.

direct: every STRATEGY.md metric is annotated "measured by the agent evaluation harness", yet the harness dossier records no precision/recall metrics, no agent evaluation harness — and .github/workflows/ci.yml publishes to FlakeHub without running any tests. The fixture variant-trigger mechanism and the synthetic-IR mutation pattern in tests/fixtures/synthetic-ir.nix are the existing raw material the kernel reuses.

Rationale: There is high confidence that an agent receiving current findings can resolve them — but no proof. The kernel converts that belief into measured catch/precision/repair/time numbers on the fixtures we already trust, which is exactly the evidence needed to ship into the field with a straight face. Scope discipline is the point: a heavier harness would delay field evidence, and the field is the better defect generator (see Grounding Context).

Downsides: Metrics over hand-picked fixtures overstate real-world performance — acceptable because the kernel's job is validating the fixtures, not characterizing the world; field intake (2c) supplies the realistic distribution.

1a. CI gate: tests before FlakeHub publish

Complexity: Low · unconditional first — day-one hygiene

Wire tests/default.nix and fixtures/run-checks.bash into CI and block flakehub-push on them. Today an engine-breaking commit ships to every consumer unvalidated.

1b. Metrics runner over existing fixtures

Complexity: Medium

A runner that takes the existing seeded fixtures, has an agent attempt resolution, and reports the four strategy metrics — catch rate, precision, repair success, time to valid repair — plus eval wall-time as a tracked performance budget. Output is a claim with numbers attached, not infrastructure.

1c. Two-tier eval split

Complexity: Low · keeps the loop affordable

Hermetic engine-only evals over synthetic IR (milliseconds, free) run in CI on every commit and guard the zero-false-positive discipline; agent-in-the-loop evals (LLM cost dominates) run on demand or nightly. The split keeps compute cost from distorting the loop's cadence.

2. Field readiness — usable in the wild, early

Bootstrap 2 adoption-surface feedback-delivery Confidence 85% Complexity Medium

Description: Make den-lsp runnable against real repos by real agents as early as possible — because the field is the lab's best defect generator, not a launch milestone at the end. Three parts: frictionless entry, an agent-consumable CLI contract, and a deliberate pipeline that turns every field failure into a fixture.

direct: a sniff-test run against a real den repo surfaced multiple bugs that clean fixtures never triggered — lab experiments control variables; agent-touched real configurations are anything but clean. The adoption dossier documents the 2-step flake-module commitment as the only entry path; the delivery dossier documents that headless output is a text report agents must scrape, and server/src/eval.rs spawns nix eval with no timeout.

Rationale: Promoted from last place after refinement: the original ranking treated distribution as something value must precede, but the sniff-test evidence inverts that — field exposure produces the evidence. Zero-touch injection additionally pays an engineering dividend: it's what lets the evidence kernel point at arbitrary un-instrumented repos. Absorbs the surviving value of the dropped MCP focus as plain CLI affordances (see Rejection Summary).

Downsides: Early field exposure means early field bug reports against a young tool — mitigated by the kernel's proof that the core findings are sound before going wide; suppressions are deliberately deferred until field evidence shows where legitimate exceptions actually occur.

2a. Zero-touch ephemeral analysis injection

Complexity: Medium

Synthesize the injection wrapper at invocation time (nix eval --expr) so den-lsp analyzes any stock Den flake — no flake input, no committed module. Try-before-adopt for consumers; arbitrary-repo analysis for the kernel and for sniff tests.

2b. Agent-consumable CLI contract

Complexity: Low–Medium · absorbs the dropped MCP focus

den-lsp-check --json with a stable findings schema and exit semantics (the machine-readable channel for Focus 3's structured payloads), plus --draft/--gate strictness flags so gating findings advise mid-draft and block at the pre-completion checkpoint — ephemeral flags, no repo config, preserving the zero-knob stance.

2c. Field-failure intake and reliability floor

Complexity: Medium · the flywheel coupling

Every real-world breakage — crash, wrong finding, hang — becomes a fixture in the eval corpus by convention, feeding the kernel the realistic defect distribution hand-seeding can't produce. Includes the reliability floor field use demands: tokio deadlines on nix eval, cancellation of superseded evaluations, timeout surfaced as a finding rather than a silent hang.

3. Machine-actionable repairs

Loop repair-guidance Confidence 85% Complexity Medium–High

Description: Move findings from "prose a model must interpret" to "edits a model can apply": structured fix payloads in the findings document, and precise source locations so the fix lands in the right file. Runs inside the loop, prioritized by what kernel metrics and field intake show agents actually failing to repair.

direct: nix/engine/document.nix defines fix as a freeform prose string; the repair-guidance dossier confirms no CodeAction handlers and no structured replacement type exist, and server/src/diagnostics.rs:56-60 falls back to flake.nix:0,0 when position data is missing — agents are sometimes told the right fix in the wrong file. Five of five ideation frames converged on structured fixes.

Rationale: Two of the four strategy metrics — successful repair rate and time to valid repair — are decided at this layer, and unlike the kernel this ships value into real repos the day it lands. The stable findings-document version field makes this a clean v2 evolution. The dry-run repair loop (apply candidate fix in an isolated eval, confirm the finding resolves) is deferred until kernel repair-rate data shows one-shot structured fixes aren't sufficient — it's the escalation, not the starting point.

Downsides: Location resolution (3b) is the hard part — mapping evaluated-graph findings back through Nix source — and structured fixes without reliable ranges are worse than prose, so 3b gates 3a's range-based payloads (template payloads can ship first).

3a. Findings v2: structured suggestedFix + LSP CodeActions

Complexity: Medium · 5× frame convergence

Extend the findings schema with machine-actionable payloads — {file, range, replacementText} or a complete ready-to-paste Nix template — alongside the existing prose. Surface via textDocument/codeAction for editors and via the 2b JSON contract for agents.

3b. AST-mapped location resolution

Complexity: Medium–High · prerequisite for range-based fixes

Parse consumer aspect files with rnix on the Rust side and map evaluated attribute paths (e.g. den.aspects.web.nixos.services.openssh) to exact line/column ranges — eliminating the flake.nix:0,0 fallback that misdirects agents into editing the wrong file.

4. Coverage expansion

Loop rule-coverage Confidence 75% Complexity Medium

Description: Grow what the engine can see, starting with the IR fields the capture layer already produces but no rule reads. Rule selection is driven by the loop — kernel learnings and field-intake fixtures identify which defect classes real agents actually produce — rather than by what's easiest to detect.

direct: the rule-coverage dossier catalogs captured-but-unused IR v1 fields — ctxTrace, scopes (parent/entityKind/contextKeys), entry lifecycle flags (excluded, excludedFrom, replacedBy), homes, registry metadata — while all six rules read none of them. Four frames converged on mining these fields.

Rationale: Catch rate ultimately depends on what rules can see, and the cheapest expansion needs zero capture-layer changes. Lifecycle rules target the strategy's motivating scenario exactly: an aspect silently displaces another, the build passes, intended behavior vanishes. Every new rule lands with its seeded fixtures and a measured precision line through the kernel (1c's hermetic tier makes this free) — that convention is what lets coverage grow without eroding the zero-false-positive discipline. Schema-derived rule synthesis stays parked until hand-written rules stall.

Downsides: Each new gating rule risks precision regressions and adds agent burden if its repair guidance lags — which is why coverage rides the loop behind repairs rather than racing ahead of them.

4a. Rules mining unused IR fields: scope + lifecycle defects

Complexity: Medium · zero IR changes needed

Scope-mismatch rules from scopes/ctxTrace (e.g. home-manager options emitted under a NixOS host scope) and displacement rules from excluded/replacedBy (silently dropped capabilities, orphaned dependents).

4b. Registry-metadata-enriched findings & hover

Complexity: Low–Medium

Pipe captured registry descriptions/provides/callable signatures into finding explanations and hover cards, so the "why" and the "what instead" arrive with the finding — zero configuration, better repair context.

Rejections first, then items deferred by the refinement pass (deliberately out of the near-term, not discarded).
